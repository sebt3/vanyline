# v0.1.1 — premier déploiement réel de la CRD Application (media-test)

Contexte : v0.1.0 venait d'être buildé/publié sur ghcr.io. Session de validation
en direct sur le cluster (namespace `media-test`, hors production) : CRDs → controller
→ Postgres CNPG dédié → client OIDC Authentik réel → CR Application. Objectif : vérifier
que le CRD `Application` (feature `controller-application-crd`) fonctionne vraiment de
bout en bout, pas juste `cargo test`.

## Bugs trouvés et corrigés (→ v0.1.1)

Quatre bugs réels révélés uniquement par un déploiement live, aucun détecté par les
tests unitaires existants :

1. **`OIDC_CA_CERT` traité comme un chemin de fichier côté `app`**
   (`app/src/auth/oidc.rs`), alors que le controller injecte le **contenu PEM inline**
   via `secretKeyRef` (`controller/src/application.rs`). Cassait tout OIDC derrière une
   CA privée — donc quasi tout usage réel hors CA publique. Fix : parser la valeur de
   l'env directement comme PEM, plus de `fs::read`.
2. **CRD `Application` sans aucun support TLS** — l'Ingress généré n'avait jamais de
   bloc `spec.tls`, indépendamment des `ingressAnnotations` fournies (cert-manager
   ignore l'annotation seule sans bloc `tls`). Ajout de deux champs obligatoires/
   optionnels : `tlsIssuerName` (String, obligatoire — on part du principe que
   cert-manager est présent, même logique que les autres apps du cluster) et
   `tlsIssuerKind` (`ClusterIssuer` par défaut ou `Issuer`). Le reconciler pose
   l'annotation `cert-manager.io/cluster-issuer` (ou `-issuer`) + `spec.tls` (secret
   `<application-name>-cert`, même convention que les autres Ingress du cluster :
   `penpot-cert`, `gitea-cert`, etc.).
3. **`databaseSecretRef` attendait une clé `databaseUrl`** que rien ne produit
   nativement — imposait un secret intermédiaire fabriqué à la main à chaque
   déploiement. Renommé en `uri`, la clé que CNPG pose nativement dans le secret
   `<cluster>-app`. `databaseSecretRef` peut désormais pointer **directement** sur ce
   secret CNPG (cas d'usage quasi systématique).
4. **Bug CI sans rapport avec les 3 ci-dessus, trouvé en cherchant à publier
   l'image `app`** : `dependabot.yml` ciblait `npm_ecosystem directory: "/frontend"`,
   mais le repo utilise des **npm workspaces** (`workspaces: ["frontend"]` en racine) —
   le lockfile qui compte pour `npm ci` (utilisé par `app/Dockerfile`) est celui de la
   **racine**, jamais mis à jour par dependabot depuis le bootstrap initial. Résultat :
   `package-lock.json` racine désynchronisé de `frontend/package.json` (reka-ui,
   @types/node bumpés) → `npm ci` en échec, image `app` invalidée, `sandbox`/
   `controller` annulés en cascade (dépendance de matrice CI). `Tests`/`Frontend`
   étaient déjà rouges sur `main` avant cette session, personne ne l'avait remarqué.
   Fix : lockfile racine régénéré, `frontend/package-lock.json` supprimé (redondant
   sous workspaces), `dependabot.yml` pointé sur `/`.

## 5ᵉ bug trouvé après coup, en testant le login réel (pas encore en v0.1.2)

En se connectant réellement via le navigateur : `/` (→ `/settings`) affichait juste le
texte brut `VNL-AUTH-001: Not authenticated` sans jamais rediriger vers `/auth/login` —
aller sur `/auth/login` directement fonctionnait, mais rien dans le frontend n'indiquait
que cette route existait. Cause : aucun endroit du frontend (routeur `router.ts`, `App.vue`,
ni le client API `api/client.ts`) ne gérait un 401 — chaque écran `settings/*.vue` affiche
l'erreur brute renvoyée par `ApiError` et s'arrête là. Fix (commit `4908f89`) : redirection
globale `globalThis.location.href = '/auth/login'` ajoutée dans `api/client.ts` (seul point
de passage de tous les appels `/api/*`), déclenchée sur tout 401. **Commité sur `main` mais
pas encore en v0.1.2** — le développeur principal veut continuer à tester avant de couper
une nouvelle release (2026-08-13, "on va continuer de creuser le problèmes existant avant de
faire une nouvelle release"). Le pod live en `media-test` sert donc toujours le frontend
d'avant ce fix tant que v0.1.2 n'est pas publié et redéployé.

## 6ᵉ bug trouvé en testant la création de projet (pas encore en v0.1.2)

`GET /api/projects` (chargement de l'onglet Projects) et `POST /api/projects` plantaient
systématiquement en 502 dès le premier appel — masquant complètement le comportement
réel côté validation d'URL git (`ProjectSpec.repo_url` accepte n'importe quelle string,
aucune restriction de format). Cause : `reqwest` (rustls-tls) et `kube` (rustls-tls,
via `vanyline-lib` feature `k8s`) tirent chacun un backend crypto rustls différent
(`ring` / `aws-lc-rs`) — les deux finissent compilés dans le binaire `app` (unification
des features Cargo, `resolver = "2"`). Sans `CryptoProvider::install_default()` explicite,
rustls panique au premier client TLS construit sans passer par le chemin déjà résolu par
reqwest — en pratique le client K8s (`vanyline_lib::k8s::VnlK8sClient`, **découvert
lazily à la toute première requête qui en a besoin**, cf. `app/src/k8s.rs`). Le panic tue
la requête en cours (process survit, tokio ne fait que perdre cette tâche), l'Ingress voit
la connexion coupée → 502 ; ça repanique à chaque nouvel appel `/api/projects` suivant,
indéfiniment. `controller` n'est jamais touché par ce bug (il ne dépend pas de `reqwest`,
feature unification scoped par binaire avec resolver v2 — un seul backend crypto dans son
propre graphe de deps). Fix (commit `86e58a7`) : `rustls::crypto::ring::default_provider().
install_default()` appelé explicitement tout en haut de `main()`, avant toute construction
de client TLS. **Commité sur `main` mais pas encore en v0.1.2** (même situation que le bug
frontend #5 — le développeur principal continue de tester avant de couper la prochaine
release).

## Process de release découvert en le déclenchant

`.github/workflows/release.yml` : déclenché par un tag git poussé sur GitHub (repo
public `sebt3/vanyline`, remote `origin`). Tague les images sur `github.ref_name` —
donc un tag `v0.1.1` produit des images `:v0.1.1` (préfixe `v` obligatoire). Le manifest
`deploy/controller/controller.yaml` avait ce préfixe faux depuis la toute première
release (`0.1.0` au lieu de `v0.1.0`) — corrigé au passage.

**Piège vécu** : le premier tag `v0.1.1` a été poussé avant d'avoir corrigé le bug
lockfile (#4 ci-dessus) → build `image (app)` en échec, `sandbox`/`controller` annulés,
mais `create-release` + `upload-cli` ont réussi (release GitHub créée sans les images).
Il a fallu corriger, puis **déplacer le tag** (`git tag -f` + `push --force` sur le tag
uniquement, jamais sur une branche) pour relancer le pipeline sur le bon commit — décision
explicite du développeur principal ("corriges, on écrasera le tag ensuite"), pas une
initiative prise seule.

## Décisions actées pour ce genre de session de validation

- Un environnement de test réel (media-test) doit être isolé de la prod
  (media-station) mais peut légitimement réutiliser des services partagés du cluster
  (Authentik dans `media-system` via RestEndPoint cross-namespace) — un cluster CNPG
  dédié reste préféré à la réutilisation d'un cluster Postgres d'une autre app, pour ne
  pas coupler le test à un service tiers.
- Un client OIDC de test n'a pas besoin de mapping de groupe/rôle Authentik
  (`resource_access`) : `app` ne lit que la claim `email` de l'id_token
  (`app/src/auth/oidc.rs`) — les scopes par défaut `openid,email,profile` suffisent,
  pas besoin de reproduire le scope mapping custom de production
  (`deploy/web/RestEndPoint_sso.yaml`, jamais réellement appliqué en prod à ce jour).

## État après cette session

`vanyline-test` (Application CR, media-test) tourne en v0.1.1, `/health` répond 200 en
HTTPS complet (cert-manager `self-sign`, CA vérifiée). `deploy/web/*.yaml` (Deployment/
Service/Ingress manuels pré-CRD, namespace media-station) reste un vestige non appliqué
nulle part — obsolète depuis que la CR `Application` fait ce travail ; à supprimer ou
migrer lors d'un futur nettoyage, pas fait dans cette session (hors périmètre demandé).
